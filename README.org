* bind-mounts: share host directories with smolvm guests
** Overview
bind-mounts is one Ansible playbook, driven by a single configuration file,
that shares host directories with
[[https://github.com/smol-machines/smolvm/][smolvm]] guests.
** Details
One default run validates the configuration, attaches the configured
host directories to each machine, bind-mounts them at their target
paths inside each guest, installs a login hook that re-applies the
mounts, verifies every mount, and records everything it created in a
provenance ledger.

The playbook manages any number of machines and users from the same
file, is safe to re-run in any state, and never touches a mount or
volume it cannot prove it created.

Two modes are supported. In bind mode the playbook consolidates every
configured directory under one share directory (share_root), attaches that
share to each machine as a single volume, and inside the guest bind-mounts
each entry from the share to its real target path, so one volume slot serves
any number of directories. In direct mode every configured directory becomes
its own smolvm volume, which is simpler inside the guest but uses one volume
slot per directory. Switching modes is a one-line configuration change:
stop the machines, change the mode, and run the playbook once; it converges
the volume set, restarts the machines, and verifies the result.

The mode choice exists because of a smolvm constraint: a directory attached
directly is its own virtiofs device, and libkrun (the VMM underneath) caps
x86_64 machines at 11 virtio-mmio IRQs, one per device. Balloon, rng,
console, and two block devices take five; the root filesystem, the volume
mounts, and the vsock agent channel share the rest, so a directly created
machine fits at most 4 host volumes (3 for machines created from a packed
.smolmachine archive), and one fewer when anything else adds a device, such
as published ports. The ceiling lives in libkrun, and smolvm has no preflight
for it; see smolvm issue
[[https://github.com/smol-machines/smolvm/issues/941][#941]].
bind mode makes the ceiling irrelevant to the number of shared directories;
direct mode is subject to it.
** Quick start
*** 1 Copy vars.yml.example to vars.yml in the repository root
The playbook looks for vars.yml in its own directory, next to
bind-mounts.yml; put it exactly there.
#+BEGIN_SRC
cp vars.yml.example vars.yml
#+END_SRC

Edit vars.yml with your machine names, users, and directories. vars.yml is
git-ignored and must never be committed; every path in vars.yml.example is
fictitious.
*** 2 Run the default playbook
#+BEGIN_SRC
ansible-playbook bind-mounts.yml -i inventory -K
#+END_SRC

-K prompts once for the sudo password, because host sudo has no passwordless
rule. The default run validates the configuration, bind-mounts the sources
into share_root, attaches missing volumes to stopped machines, starts each
machine if it is stopped, installs the login hook, applies the guest-side
bind mounts, and verifies the result. The guest may be running or stopped; a
stopped machine is started automatically, so nothing needs to be stopped or
started by hand first. A running machine that needs a volume change halts
the run with a boxed ACTION REQUIRED message naming the machine and the
command to run; stop it and re-run.
*** 3 Log in and use the machines
Log in as usual with smolvm machine exec. The mounts are already in place,
and the installed .bash_profile hook re-applies them non-interactively at
every login as a fallback.
** How to
*** Add a volume
Add a mount entry under the machine in vars.yml and run the default
playbook. Whether the guest can stay running depends on the mode.
**** Bind mode: the guest can stay running
The new directory rides inside the existing share volume, so the run
creates the share subdirectory, bind-mounts it on the host, creates the
target directory in the guest, and binds it from the share, all while
the machine runs.
**** Direct mode: the guest must be stopped
The new mount becomes a new volume, and volume changes require a stopped
machine. A stopped machine is converged during the run; a running machine
halts the run with an ACTION REQUIRED message, so stop it and re-run.
*** Remove a volume
Delete the mount entry from vars.yml and run the default playbook. Guest
target directories are never removed and no data is deleted in either
mode. Whether the guest can stay running depends on the mode.
**** Bind mode: the guest can stay running
The run unmounts everything the ledger proves it created: the host-side
bind, the emptied share subdirectory, and the guest-side bind.
**** Direct mode: the guest must be stopped; the volume itself is removed
*** Change a volume
Changing the target path or the share name converges automatically.
Whether the guest can stay running depends on the mode.
**** Bind mode: the guest can stay running; the old binds are replaced in place
**** Direct mode: the guest must be stopped for the volume re-creation
**** Manual preparation for source and readonly changes
Two kinds of change need a manual unmount first. Both apply when the
share name stays the same; a mount whose share name also changes is torn
down and rebuilt automatically instead.
***** Changing the source directory while keeping the share name
The identity check compares the configured source against what the share
subdirectory is bound from, and the check fails with a foreign-mount
message. Whether the target path also changes makes no difference: the
failure keys on the source and the share name alone.
***** Flipping readonly on an already-mounted pair is not applied automatically
The new setting takes effect only when the pair is mounted fresh. The
share name staying the same is what makes it an already-mounted pair.
***** Recovering: unmount the old bind pair or stop the guest
The host bind is unmounted on the host; the guest bind is unmounted
through smolvm machine exec. Stopping the guest instead clears its binds
at once. Then edit and re-run.
** Configuration reference
The block below shows the shape of vars.yml; every path in it is a fictitious
example. Copy vars.yml.example to vars.yml and replace names, users, and
directories with your own.

#+BEGIN_SRC yaml
mode: bind
share_root: /home/you/share
share_target: /mnt/share
machines:
  - name: my-vm
    user: you
    uid: 1000
    gid: 1000
    profile_path: /home/you/.bash_profile
    max_volumes: 4
    mounts:
      - name: website
        src: /home/you/projects/website
        target: /home/you/projects/website
        readonly: false
        uid: 1000
        gid: 1000
#+END_SRC
*** mode selects bind or direct operation
*** share_root holds the per-mount subdirectories and the ledger
It is required in both modes and must be an absolute path without whitespace.
*** share_target is the guest path of the share root in bind mode
*** machines holds one entry per smolvm machine with unique names
**** user plus uid and gid select the account and created-dir ownership
**** profile_path defaults to the bash profile of user in the guest
**** max_volumes caps the volume slots per machine
The default is 4. Machines created from a packed .smolmachine archive fit 3,
and every extra device, such as published ports, costs one more slot; hand
attached volumes count against the cap just like playbook-managed ones.
**** mounts lists the shared directories
***** src is the host directory and must exist before the run
***** target is the absolute guest path, unique per machine
***** name is the share subdirectory name in bind mode
It defaults to the last path component of src. The same name and src pair on
several machines means those machines share the subdirectory.
***** readonly is optional in both modes
Direct mode appends :ro to the volume; bind mode remounts the bind read-only.
***** uid and gid override created-directory ownership
They default to the machine-level uid and gid.
** Tag reference
*** The default run
Validate, volume convergence for stopped machines, host binds, start,
install, guest binds, verify. Works whether the guests are running or
stopped; a running machine that needs volume changes halts the run with an
ACTION REQUIRED message naming the machine and the command to run.
*** mounts
Host binds and guest binds only. Refuses stopped machines, because guest
binds need a running guest.
*** install
Refreshes the guest script, the sudoers drop-in, and the profile hook. Needs
running machines and a root exec user.
*** start starts stopped machines and waits for exec readiness
*** verify checks every mount read-only after the run
*** attach converges the volume set; machines must be stopped
The default run already converges stopped machines automatically, so attach
is only needed for explicit, step-by-step control.
*** stop syncs each guest and stops the machines
Tolerates machines that are already stopped.
*** teardown undoes everything the playbook created
Direct-mode volume removal requires stopped machines.

attach, stop, and teardown are excluded from the default run; select them
explicitly with --tags.
** Mode switching
*** 1 Stop the machines
#+BEGIN_SRC
ansible-playbook bind-mounts.yml -i inventory --tags stop
#+END_SRC
*** 2 Change the mode or the mount list
Edit mode and the machines list in vars.yml.
*** 3 Run the default playbook
#+BEGIN_SRC
ansible-playbook bind-mounts.yml -i inventory
#+END_SRC

The run converges the volume set on the stopped machines and starts them
again. Bind to direct: every mount becomes a volume, the share volume is
removed, and the guest-side login hook, sudoers rule, and installed script
are removed. Direct to bind: the share volume is attached and former mount
volumes are removed. Only volumes the ledger proves the playbook created are
ever removed; hand-attached volumes, such as a persistent home directory, are
untouched but still count against max_volumes.

For step-by-step control you can still converge explicitly with --tags
attach after stopping, and start the machines with --tags start.
** Safety model
*** The provenance ledger records everything the playbook creates
The ledger lives beside the share subdirectories and records volumes, host
binds, guest binds, and installed artifacts per machine. Entries that are in
the ledger and in the configuration are maintained; entries in the ledger but
no longer in the configuration are removed; anything else is foreign and
never touched. On the first run, existing mounts that match the
configuration are verified and adopted into the ledger.
*** Foreign mounts are refused, never unmounted automatically
A target already mounted with different content than the configured source
fails the run with the found and expected device:inode identities printed,
together with the manual resolution path.
*** Idempotency compares device and inode, not just mount presence
Every check compares the device and inode of the mounted target against the
configured source, so a stale or wrong-source mount is caught instead of
silently skipped. Source-path comparison is deliberately avoided because the
kernel reports bind sources in normalized form that cannot be matched by
string equality.
*** Volume changes fail on running machines instead of stopping them
The attach tag refuses running machines and prints the exact commands to run;
the playbook never stops a machine with live sessions on its own.
*** The sudoers rule is scoped to a root-owned script copy
The login hook runs sudo -n against the root-owned 0755 copy of the script.

#+BEGIN_SRC
<user> ALL=(root) NOPASSWD: /usr/local/sbin/bind-mount-on-guest.sh
#+END_SRC

The drop-in is validated with visudo before activation. The rule authorizes
only the root-owned copy at /usr/local/sbin, so nothing under the
user-writable share can run with NOPASSWD root privileges.
*** Writes are atomic and preserve ownership and mode
Ledger and profile edits go through a temp file and rename. The profile
helper preserves the file owner and mode and never touches lines outside the
managed block, which uses the standard blockinfile markers.

** Shutdown semantics
smolvm machine stop is graceful: the guest agent runs a full sync, flushing
every filesystem including virtiofs, remounts the storage read-only to
checkpoint its journal, and only then is the VMM terminated, after which the
host fsyncs the disk files. Guest processes get no chance to clean up; it is
sync-then-kill, like pulling power after sync, so save editor buffers first.
The stop tag adds a redundant guest sync before stopping as belt-and-braces.
** Glossary
*** Bind mode
One share volume per machine; each configured directory is bind-mounted
into the share root on the host and from the share to its target path
inside the guest.
*** Direct mode
Each configured directory is attached as its own smolvm volume, with no
share volume and no guest-side artifacts.
*** Device:inode identity
The pair of device and inode numbers reported by stat. Equal identity
means two paths reference the same content; this is how bind mounts are
verified, because bind sources cannot be compared as strings; the
kernel reports them in normalized form.
*** Exec user
The user as whom smolvm machine exec runs commands inside a guest.
Management operations require it to be root.
*** Foreign state
Any mount, volume, or file the ledger cannot prove the playbook created.
Refused or ignored, never removed.
*** Guest bind: a bind mount from the share path to the target path
*** Guest-side share path: share_target followed by the mount name
*** Host bind: a bind mount from a source directory to its share subdirectory
*** Ledger
The file .bind-mounts-state.yml inside the share root. It records
everything the playbook created, is written at the end of a successful
run, and is read at the start of the next; it is the basis of provenance
and stale-element cleanup.
*** Login hook
The managed block in the machine user's .bash_profile that re-applies
the guest binds at every login through passwordless sudo.
*** Mount entry: one host directory plus its guest target path in vars.yml
*** share_root: the host directory holding one subdirectory per mount entry
*** share_target: the guest path at which the share root is mounted
*** Share volume: the one smolvm volume backed by the share root
*** Stale element: ledger-proven state the configuration no longer lists
*** Volume: a host directory attached to a machine as its own virtiofs device
** Troubleshooting
*** A missing vars.yml fails fast with copy instructions
*** A target mounted with a different source needs manual resolution
Unmount the foreign mount, or run the teardown tag for ledger-managed binds,
then re-run the playbook.
*** Refused volume changes mean stop, then re-run
The playbook never stops a machine with live sessions on its own. Re-run
after stopping: the run attaches the volume, starts the machine, and
finishes the rest.
*** An exceeded volume budget counts hand-attached volumes too
Remove mounts from vars.yml, or raise max_volumes only if you know the
machine has headroom; see smolvm issue
[[https://github.com/smol-machines/smolvm/issues/941][#941]].
*** An unreadable ledger disables cleanup for that run
Fix or delete the ledger file; deleting it loses only the cleanup
bookkeeping.
*** The smolvm exec user must be root for the playbook to manage a guest
**** Context
The playbook reaches a guest only through smolvm machine exec, which runs
as the exec user configured on the machine. Installing the login hook
writes root-owned files (the script under /usr/local/sbin and the
sudoers drop-in), and the guest-side mounts need root.
**** Cause
The machine's configured exec user is not root, typically because it was
created with a non-root --user default; the playbook fails the run
with the machine's uid in the message.
**** Solution
Create or update the machine without a non-root --user default, then
re-run the playbook.
